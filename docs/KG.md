# The observation graph: Sounds of Home as a SAREF knowledge graph

**What it is.** Every 10 s window of every hour of the Sounds of Home dataset (14 recorders, 7 homes,
7 days each, 1,344 hours) as an RDF observation, structurally identical to the DAHCC Homelab graph
(IDLab Ghent): the microphone is the sensor, the sound class is the measured property, the PANNs
confidence is the value. One N-Triples file per recorder-day in `data/real/kg/`, plus a frame-level file
for one hour (`frames_14_20231122_130000.nt.gz`) that carries the raw top-7 predictions at 0.21 s, the
evidence layer beneath the segments. Build everything with `scripts/build_all.sh`; the numbers below
come from `data/real/report.md`, which that script regenerates.

## Schema (per observation)

| predicate | object | DAHCC equivalent |
|---|---|---|
| `void:inDataset` | `<base>/<recorder>_<date>` | `<Protego/_participantN>` |
| `saref:measurementMadeBy` | `<base>/mic/<recorder>` | `<Homelab/SensorsAndActuators/<sensor>>` |
| `saref:relatesToProperty` | `<base>/property/activity/<Class>` or `.../background/<Class>` (`activity/none` for quiet, masked or unidentified windows) | `<.../org.dyamand.types.common.Loudness>` etc. |
| `saref:hasTimestamp` | window start, `xsd:dateTime` | same |
| `saref:hasValue` | PANNs peak probability of that class in the window, `xsd:float` (0 for privacy-masked windows) | sensor reading |
| `rdfs:label` (activity obs only) | the one-sentence description | – |
| `prov:wasDerivedFrom` (activity obs only) | `<base>/clip/<stem>_<seg>_wav`, the 10 s clip | – |

A window with both an activity and a background yields two observations sharing the timestamp.
The timeline is gapless: masked windows are `activity/none` with value 0 and the label
"Audio unavailable (privacy-masked)."; quiet windows carry EchoScriptor's null sentence; windows where
nothing passed the thresholds carry "Unidentified sounds." Downstream code can therefore distinguish
*no evidence* from *evidence of nothing*.

Classes follow the notebook's `extended` taxonomy (EchoScriptor's 24 activities and 8 backgrounds plus
television, doors, drawers, cutlery, clock, writing, snoring; speech and music cannot occur because the
dataset blanked them). Thresholds and maps are generated from the reviewed notebook into
`soh/taxonomy.py`; `scripts/test_taxonomy.py` fails if they drift.

## How it is built (notebook Stages 2-5, without audio)

1. `soh/panns.py::load_annotation` reads the hourly JSON (16,852 frames, top-7 classes each; absent = 0).
2. `privacy_mask`: any of the ten speech/music labels >= 0.20, dilated by 1 s each side, marks frames that are
   digital silence in the released WAV.
3. `segment_hour`: per 10 s window and per taxonomy label, take the per-frame max over the label's AudioSet
   aliases, then peak and coverage (fraction of frames >= 0.20). Activity if peak >= 0.50 and coverage >= 0.30;
   background if peak >= 0.30 and coverage >= 0.50; > 2 % masked frames drops the window as `privacy_masked`;
   >= 80 % silence-like frames makes it `null`; otherwise `no_confident_label`.
4. `scripts/timeline_to_captions.py` turns those rows into contract records (the same code path Sarita's
   audio pipeline uses), and `scripts/captions_to_nt.py` writes the triples.

Recorder-to-home mapping is not published. `panns_to_captions.py` infers it: two recorders that recorded
the same dates were in the same home (the dataset placed two AudioMoths per home), and the one with the
larger share of kitchen-class windows (tap, cutlery, microwave, chopping, dishwasher, timer) is called
the kitchen. `data/real/recorders.json` carries the evidence; treat it as a hypothesis until the dataset
owners confirm.

## Querying it

`python scripts/kg_query.py data/real/kg/captions_14_20231122.nt.gz` runs six questions in SPARQL:
what was heard and how often; when the tap ran; doors after 18:00; how much of the day is masked;
which clips back an observation (provenance); and a question about keys, which returns zero rows, the
correct answer being "no evidence". Detection, counting and temporal questions are answerable in plain
SPARQL on this graph. State questions ("is it still running?"), absence reasoning and calibrated
abstention are not: they are the reasoning layer's job (`graph/`, `qa/`), which reads these observations
through the query API.

## The event graph (the DAHCC event-graph shape)

`graph/eventgraph.py` re-expresses a recorder-day as an event-centric graph and `scripts/event_graph_view.py`
draws it (one page and one `events_<rec>_<date>.nt.gz` per day, linked from the index):

```
Event_k  --hasPreviousEvent-->  Event_{k-1}          Event_k hasActivity "label"; hasTimestamp; hasEndTimestamp; confidence
Event_k  --has<Appliance>State-->  State              depth 1: appliance States overlapping the event, and the room's state during it
State    --hasObs-->  Obs                              depth 2: the observations the state rests on = the SAREF observation IRIs above
Obs      --hasSensor / hasValue / hasClip-->  leaves   depth 3
```

An Event is an activity episode (ActivityBlock) of the temporal graph, so the chain is the sequence of
activity transitions through the day. Vocabulary: `https://home-audio-kg-bench.org/ev#`. Because the
`Obs` nodes are the same IRIs as the observation graph, one SPARQL store holds both layers and a
question like "what was happening before the door?" is a two-hop query:

```sparql
SELECT ?before WHERE { ?e ev:hasActivity "Opening or Closing a Door" ; ev:hasPreviousEvent ?p . ?p ev:hasActivity ?before }
```

Recorder 10 on 2023-11-22: 67 events, 117 states, 493 observations, 3,989 triples.

## The frame-level layer

`scripts/panns_frames_to_nt.py` exports one hour at DAHCC's own granularity: 16,852 frames x top-7
classes = 117,963 observations, 589,815 triples, 2.5 MB gzipped. Every segment observation could point
at the frames it was aggregated from; we keep that layer optional because 1,344 hours of it is ~800 M
triples and the reasoning layer never needs it, but it is the right place to drill down when a human
verifies a clip.

## SINS: the human-labelled counterpart

`data/sins/sins_dev.nt.gz` and `sins_eval.nt.gz` hold the DCASE 2018 Task 5 metadata (SINS: one person,
one real home, one week, 4 microphone nodes) as the same observation shape with human activity labels
(value 1.0) and a `session` link. The release has no clock time and its session ids are grouped by
activity, so each session gets its own relative clock from 1970-01-01T00:00:00; within a session the
order is real. It is ground truth for activity *episodes* (durations, node agreement), not for
clock-time questions. Dev: 72,984 segments, 266 sessions, 437,904 triples. Eval: 72,972 segments, 131
sessions, node ids withheld by the organisers.

## How this compares with DAHCC

Same five predicates, same one-observation-per-reading shape, same per-participant/per-day file
layout, so `scripts/kg_timeline.py` renders both and one SPARQL query runs on either. The differences
are the point of the project: DAHCC's values are true readings from 275 wired sensors; ours are
probabilities from one microphone, with a privacy mask that removes about a sixth of the audio. DAHCC
has no audio at all; Sounds of Home has nothing but audio.

## Reproduce

```
scripts/build_all.sh            # downloads the 1.05 GB labels package + SINS metadata, runs tests, builds everything
python scripts/kg_query.py data/real/kg/captions_14_20231122.nt.gz
open data/real/kg/index.html    # one timeline page per recorder-day
```
